# endolphin — プロダクト定義 v1（設計仕様）

- **日付**: 2026-06-18
- **ステータス**: ドラフト。**Phase 1 実装済**（PR: tiramiss-community/endolphin#2）。**Phase 2 実装中（チャート削除）**。互換方針（§3 P3 / §5）は実装時に「entity・migration は温存 / write は ApiError 化」へ refine した（本文反映済）。**チャンネルは Phase 2 着手時に「残す」へ変更**（§4 参照。削除対象 8 → 7 機能）。**`claimAchievement()` 散在呼び出し点は no-op のまま温存**（物理除去は最ホットコア ~15 ファイルに及び P2 と衝突するため見送り。Phase 1 で関数は既に no-op 化済み）。
- **スコープ**: Phase 0–3（プロダクト定義 = 機能厳選とクライアント厳選まで）。基盤刷新（Phase 4+）は別サブプロジェクトとして後続 spec に分離。
- **次工程**: 本 spec 承認後、各フェーズ／削除機能ごとに writing-plans で実装プランを作成。

---

## 1. コンセプト

かつての **dolphin** の精神を継ぐ、**小規模コミュニティ向けの軽量 Misskey fork**。
ブランド名は **endolphin**（dolphin + endorphin のもじり）。

機能を厳選し「これだけあればいい」体験に絞る。本家 Misskey の ActivityPub 連合と REST API 互換は維持し、Fediverse / 既存エコシステムから孤立しない。

## 2. ターゲット / 非ターゲット

- **対象**: 知人・趣味でつながる 〜数百人規模のサーバ。リスト / アンテナ / 最小限のモデレーションは必要。
- **非対象**: 数千〜数万人の大規模公開インスタンス、企業運用、本家のフル機能を求める層。

ターゲットが「小規模コミュニティ」であることが、全ての「削るか残すか」判断の物差しになる。

## 3. 設計原則（全判断の上位ルール）

### P1. 厳選UXファースト
削るのは **機能単位**（画面・サブシステムを丸ごと落とす）。
パワーユーザーが愛する UI アフォーダンス（デッキの多カラム等）は剥がない。厳選は「機能の数」を絞ることであって「UI の自由度」を削ることではない。

### P2. 追従コスト ∝ 本家更新頻度
高 churn 部（タイムライン / ノート / 投稿 / ドライブ / 連合）は **流用し続ける**。
低 churn 部（オンボーディング / About / 一部設定画面、削除対象機能）のみ自作・削除・改変してよい。

> この原則の帰結として、Hono 移行・脱 NestJS・依存解消といった **高 churn なコア基盤への改変は後回し**になる（Phase 4+）。アーキテクチャを本家から離すほど cherry-pick が「翻訳」になり追従コストが跳ね上がるため。

### P3. 互換維持
- **連合**: ActivityPub は **本家完全準拠**。連合挙動を一切divergeさせない。
  - 削除対象 7 機能（お気に入り / ページ / ギャラリー / 実績 / Games / チャート / 埋め込み）は **いずれも ActivityPub 連合オブジェクトではなくローカル機能**であるため、完全準拠と全削除は両立する。
- **API 互換**: 削除分を除いた Misskey REST API 互換を保ち、misskey-js と既存サードパーティアプリが動く状態を壊さない。
  - 削除機能の **read 系 endpoint は残し、no-op で空を返す**（空配列 / null / 既定値）。サードパーティアプリがエンドポイント呼び出しで落ちないようにするため。
  - **write 系 endpoint（create / update / delete 等）も endpoint-list 登録を維持したまま、`FEATURE_REMOVED`（HTTP 410）を返すスタブにする**。物理削除すると misskey-js から型が消え、POST が 404 になって既存クライアントを壊すため（当初案の「write は削除」から refine）。
  - read / write とも endpoint は endpoint-list に登録したまま残し、misskey-js も型を生成し続ける。
  - **entity / テーブル / migration / JSON schema / repository は温存する**（DB・型互換を維持し、破壊的な drop migration を作らない）。削除するのは業務 service・packing service・フロント UI と、未使用化した repository provider のみ。read/write スタブは削除済みの service を参照せず静的に返す（当初案の「entity / migration も削除」から refine）。

## 4. 機能セット（確定）

| 区分 | 機能 |
|---|---|
| **残す** | カスタム絵文字 / リアクション / ドライブ / Play(Flash) / リスト / アンテナ / ActivityPub / クリップ / デッキ / **チャンネル(channels)** / （未言及のコア: ノート・投票・リノート/引用・フォロー・通知・検索・ハッシュタグ/トレンド・ロール・モデレーション・2FA/passkey・アナウンス・通報・登録/招待・Webhook/APIトークン・テーマ 等） |
| **削る** | お気に入り(favorites) / ページ(pages) / ギャラリー(gallery) / 実績(achievements) / Games(リバーシ等) / チャート(charts) / 埋め込み(embed) / **管理DB統計 / リテンション分析 / 広告・プロモ（Phase 4a 追加）** / **チャット(chat)（Phase 4b 追加）** |

> **チャンネル(channels) は当初「削る」に分類していたが Phase 2 着手時に「残す」へ変更した**（2026-06-19）。理由: (1) ターゲットの〜数百人規模コミュニティでは話題整理機能（リスト/アンテナと同種）として価値があり §4 既定ルール「明らかに冗長でなければ残す」を満たす、(2) チャンネルは削除候補中で唯一ノート生成/タイムラインの最ホットコアに深く結合しており、削除は P2（高 churn コア改変は追従コストを跳ね上げる）と衝突する、(3) 残す→後で削除は容易だが削除→復元は高コストで可逆性に劣る。これにより当初の削除対象は 8 → **7 機能**。

> **Phase 4 機能削減（2026-06-20）で「削る」に追加**: §9.4 のレビュー結果（`~/.claude/plans/ph3-bright-tome.md`）として、全機能を 10 ドメイン並列調査・敵対的検証し 3 原則でティア分けした上で、Tier A（**管理DB統計 / リテンション分析 / 広告・プロモ** — 自己完結・小規模に無価値・連合無影響）と **チャット** を削除対象に追加した。いずれも Phase 1–3 と同一の削除コントラクト（read=空 / write=410 / entity・migration・型温存・enum 非縮小）で行う。Tier B（statusbar / sounds / AiScript 拡張面 / theme-install / custom-css）は **残す**（将来候補・保留）。アバターデコレーション / モデレーション・ロール簡略 / アカウント移行（連合密結合で削除不可）は据置。**「Phase 4a/4b」（本 spec 由来の機能削減）と §6 の「Phase 4+」（基盤刷新サブプロジェクト = Hono / 脱 NestJS）は別物**。
| **後回し**（別サブプロジェクト / Phase 4+） | Fastify→Hono 移行 / 脱 NestJS・自作軽量DI / ボトルネック処理の独自改良 / 循環参照・依存解消リファクタ |

> 「未言及のコア」機能の既定ルール = **明らかに冗長でなければ残す**。最終的な keep/remove は Phase 1 冒頭の機能インベントリ（§9）に対して確定させる。

## 5. 削除実行方式：C（churn 駆動ハイブリッド）

機能を削る方法は一様でない。追従コストと軽量さのトレードオフに対し、**方式 C** を採用する:

- **葉機能は「アプリ層削除 + endpoint スタブ化」**: 業務 service・packing service・フロント UI を物理除去し、read endpoint は空を返す no-op スタブ、write endpoint は `FEATURE_REMOVED`(410) スタブにする。**entity / テーブル / migration / JSON schema / repository は温存**（§3 P3。DB・型互換維持・drop migration なし）。
- **ホットなコアに絡む機能は依存を切ってから段階的に削除**。
- 埋め込みのように endpoint を持たず別パッケージで完結する機能は、パッケージ・配信ルート・ビルド機構ごと撤去する。

> **Phase 1 実装での refine**: 当初は「低 churn 葉機能はハード削除（entity / migration も物理除去）」を想定していたが、DB 互換維持と追従コスト最小化のため **entity・migration は温存し、アプリ層のみ削除する方式**に変更した。

### 削除トリアージ表（Phase 1 実装結果を反映）

| 削除対象 | 絡み方 | 方式 |
|---|---|---|
| ギャラリー / ページ / Games / お気に入り | 葉・自己完結・低 churn | **アプリ層削除**（entity 温存 / read=空スタブ・write=410 スタブ / service・UI 削除）✅Phase 1 |
| 埋め込み | endpoint なし・別パッケージ（`packages/frontend-embed`） | **完全撤去**（パッケージ・`/embed*` 配信ルート・ビルド機構ごと）✅Phase 1 |
| 実績 | `claimAchievement()` 呼び出しがフロントの高 churn ファイル（MkNote/MkPostForm/MkFollowButton/MkDrive 等 ~15 ファイル）に散在 | **no-op 化**（`claimAchievement` 無効化 + AchievementService 削除、通知型は inert 維持）。**散在呼び出し点は no-op のまま温存**（物理除去は P2 と衝突するため見送り）✅Phase 1 |
| チャート | 集計フックが各サービスに散在、エンジンは比較的自己完結 | **集計フック除去 → エンジン実行部削除**（`getJsonSchema`/entity は型・DB 互換のため温存、read endpoint は空チャートを返す）— Phase 2 |
| ~~チャンネル~~ | ノート生成 / ストリーミング / TL に深く統合（最ホットコア） | **残す**（§4 参照。削除せず本家のまま）— 方針変更 2026-06-19 |

> 各機能の正確な絡み方（呼び出し点・依存）は、実装プラン作成時に grep ベースで確定する。

## 6. フェーズ計画（本 spec のスコープ = Phase 0–3）

### Phase 0 — fork 基盤
- upstream（本家 Misskey）remote の設定と、定期マージ / cherry-pick の追従フロー確立。
- 版管理・CHANGELOG 方針、endolphin としてのブランディング適用方針（暫定で可）。
- 「本家完全準拠」を検証するための連合テスト（`test:fed`）の維持方針。

### Phase 1 — 機能インベントリ + 低 churn 葉の削除 ✅実装済（PR #2）
- **インベントリ作成タスク**（§9）: 全 endpoint / 画面を列挙し keep / remove / no-op を分類した表を作る → `docs/endolphin/feature-inventory.md`。
- 葉機能の削除: ギャラリー / ページ / 実績 / Games / お気に入り / 埋め込み + 対応 UI（§5 の方式どおり、entity・migration 温存・アプリ層削除）。
- 削除機能の read endpoint を no-op スタブ、write endpoint を `FEATURE_REMOVED`(410) スタブ化。
- 埋め込みはパッケージ・配信ルート・ビルド機構ごと撤去。

### Phase 2 — コア絡みの削除（チャートのみ。チャンネルは残す）
- **チャート** を依存切り（集計フック除去）してからエンジン実行部を削除。`getJsonSchema`/entity は型・DB 互換のため温存し、read endpoint は空チャートを返す。
- チャートの集計フック（`*Chart.update()` 等）を各サービスから物理除去。
- **`claimAchievement()` 散在呼び出し点は no-op のまま温存**（当初は除去予定だったが、最ホットコア ~15 ファイルに及び P2 と衝突するため見送り。Phase 1 で関数は no-op 化済みなので無害）。
- **チャンネルは残す**（§4・§5 参照。当初の「依存切り→削除」を撤回）。

### Phase 3 — クライアント厳選
- reuse-minus: 削除機能の画面除去とナビゲーション簡素化。
- 低 churn ページ（オンボーディング / About 等）の自作。
- 高 churn 部（TL / ノート / 投稿 / ドライブ / 絵文字ピッカー）は流用維持。

### Phase 4+（別 spec / 別サブプロジェクト）
- 基盤刷新: Fastify→Hono / 脱 NestJS・自作 DI / ボトルネック改良 / 循環参照解消。
- P2 のゲート（高 churn コアへの改変は追従コストに見合うか）を満たす範囲で着手。
- 各々が独立した spec → plan → 実装サイクルを持つ。

## 7. スコープ宣言

本 spec は **Phase 0–3 のプロダクト定義** までを範囲とする。
基盤刷新（Phase 4+）は **独立したサブプロジェクト**として、別途 spec を起こす。
各削除機能・各フェーズの具体的実装手順は、本 spec 承認後に writing-plans で plan 化する。

## 8. 成功基準 / 非目標

### 成功基準
- 削除対象 7 機能が方式 C に沿って除去され、残機能が壊れない（チャンネルは残す）。
- 削除機能の endpoint は登録・型を維持し、read は空・write は `FEATURE_REMOVED`(410) を返して既存サードパーティアプリが落ちない（misskey-js の endpoint / entity 型が消えない）。
- entity・migration を温存し DB 互換を保つ（破壊的 migration なし、`check-migrations` green）。
- 本家追従マージが現実的なコストで回る。
- ActivityPub 連合が本家完全準拠を保つ（`test:fed` が通る）。

### 非目標（v1）
- 性能改善の数値目標達成（軽量化は Phase 4+ の主題）。
- 基盤刷新（Hono / 脱 NestJS）。
- 新規 UI 体験の刷新（reuse-minus が原則）。

## 付録A. 連合非影響メモ

削除対象 8 機能が ActivityPub 連合に影響しない根拠（= 本家完全準拠と両立する根拠）:

- お気に入り / クリップ（クリップは残す）/ 実績 / チャート / Games: ローカル専用、AP オブジェクトなし。
- ページ / ギャラリー: Misskey 独自機能で標準 AP オブジェクトとして連合しない。
- 埋め込み: 外部サイト向け表示機能で連合とは無関係。
- （チャンネルもローカルオンリーで連合されないが、**残す**ことにしたため削除対象外）

> 削除対象 7 機能はいずれも連合に影響しないため、Phase 2（チャート削除）でも連合上の個別精査は不要。実装プランではローカルのデータ/UI 依存切りのみに集中する。
