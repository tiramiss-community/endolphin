# WSL2 の QEMU/KVM で Ubuntu を検証する

QEMU/WSL2 を選んだ場合の、今回の検証で再利用できる注意点。VM 作成の一般的なチュートリアルではない。

- `/dev/kvm` の存在だけで KVM 利用可能とは判定しない。実行ユーザーの権限と、QEMU プロセスからデバイスを開けることを確認する。ホストに sudo 権限がなくても、Docker が使えれば `/dev/kvm` を渡した使い捨てコンテナで QEMU を動かせる場合がある。
- Ubuntu の公式 cloud image と公開 checksum を照合する。cloud-init の使い捨て SSH 鍵、各 VM 固有のコピーオンライトディスクを使い、ホストの秘密鍵や既存データをゲストにマウントしない。ホストへの転送ポートは原則ループバックに限定する。
- systemd 用、Docker 用、復元先など、状態を共有すると検証が曖昧になる役割は別 VM にする。失敗調査では該当ディスクを保持し、再試行時は必要に応じてクリーンなディスクから始める。
- ゲストで Docker を起動すると、そのデフォルト bridge と QEMU 側の転送元アドレス帯が重なり、起動後に SSH が届かなくなることがある。経路とアドレス帯の重複を調べ、ゲスト Docker の bridge を重ならない私的 subnet にして再検証する。無関係なホストの Docker 設定は変更しない。
- ゲスト内の loopback 接続が成功しても、外部からの到達性を示さない。Nginx 経由の公開ポートと、直接公開してはいけないアプリポートの両方を VM 外から確認する。ファイアウォールは IPv4 と IPv6、再起動後の状態を確認する。
- UNIX socket 構成では、アプリがクライアント IP を必要とする API に到達するまで不具合が見えない場合がある。今回の Ubuntu 26.04 / 対象リリースではログイン経路の `request.ip` が未定義になった。将来も同じ実装とは限らないため、接続方式の一般則にせず、ログインを含む代表 API の実動作で判定する。
- 検証終了時は QEMU コンテナ、ディスク、cloud-init データ、使い捨て鍵、ポート転送を片付ける。残存 VM、コンテナ、使用容量を確認する。
